How Computers Fake Randomness

The modern world is built on computers. While computers are very complicated machines, there are various recurring fundamental problems computers are tasked with that underpin the foundation of our modern world. One of these tasks appears so intuitive, yet is something computers cannot easily solve: generating a random number.

In our world, generating a random outcome is relatively easy: roll a dice, flip a coin, or spin a wheel. However, even these outcomes are not truly random — they are modelled by the laws of physics. True randomness occurs in processes that are practically or literally impossible to model: atomic radioactive decay, thermal noise, etc.

While some computers generate hardware random numbers using these methods, these are not widely present and typically too slow for usage in modern computing.

Consequently, computers typically use pseudo-random number generators. These generators use applied statistics to operate on some sequence of numbers to return a new sequence of numbers which is statistically indistinguishable from true randomness, called Pseudo-Random-Number Generators (PRNGs). These PRNGs have far-reaching applications from cryptography (which underpins much of cybersecurity), computer simulations, gambling, and many others.

Different applications have different requirements on what is considered a "good" random number generator. For example, some methods are reversible, meaning the algorithm can be reverse-engineered from a sequence of generated numbers. A computer simulation might not care as long as the numbers are statistically random; however, this predictability would be catastrophic in cases such as securing banking transactions.

This explainer focuses on two primitive types of PRNGs: Linear Congruential Generators (LCGs) and Multiple Recursive Generators (MRGs).

If you are not mathematically inclined, do not worry: this explainer is designed to be accessible.

The Linear Congruential Generator

The oldest and simplest PRNG is the LCG, introduced by Lehmer in 1949. The term LCG defines a set of generators defined by three constant integer values:

  • \(a\), the multiplier;
  • \(c\), the increment; and
  • \(m\), the modulus.

Once defined, the generator takes an integer seed value \(X\) and generates a stream of pseudo-random numbers by recursive application of:

\[ X_0 = X \] \[ X_t = (a X_{t-1} + c) \ \text{mod}\ m \]

where \(X_t\) is the \(t\)'th random number.

Computers typically find values in the range \([0, 1)\) more useful, so the generator returns the normalised result of

\[ U_t = \frac{X_t}{m}. \]

Applying this process recursively generates a stream of numbers: each output becomes the next step's input. That's because the generator is deterministic: with a fixed formula and a fixed seed, every future output is already decided before it's computed — there's no hidden randomness left to vary between runs.

While this generator produces numbers that look random, it has a real problem: the sequence eventually repeats itself. Take \(a = 3\), \(c = 0\), \(m = 10\), starting from the seed \(X = 1\):

The values repeat themselves after just 4 iterations. This is a problem, because once they repeat, our numbers no longer look random — the sequence has nothing left to give. The number of values a generator produces before repeating is called its period.

When we run computer simulations, it's important that our numbers stay unpredictable for as long as the simulation runs. We can maximise an LCG's period by making m a prime number and a a primitive root modulo m — but even then, the period is at best m − 1, because the nonzero remainders modulo a prime m form a group of exactly that size, and repeated multiplication can never produce anything outside it. That sounds like a lot — our earlier example already reaches 2,147,483,646 — but the standard for serious simulation work is a period on the order of 10⁵⁰, because a single run can consume billions of random numbers, repeated across many runs, and a period anywhere near what a plain LCG offers risks the sequence quietly looping back on itself partway through.

So, we need a better structure.

The multiple recursive generator

An LCG's entire state is one number — whatever it just output. That's also its weakness: with so little memory, the sequence of triples \((U_t, U_{t+1}, U_{t+2})\) from an LCG can fall into visible geometric structure instead of filling space evenly, no matter how you choose a, c, and m.

A multiple recursive generator (MRG) of order k fixes this by remembering the last k outputs instead of just one — a moving window of state that slides forward one value at a time. There's no increment term; each new value is a weighted sum of everything currently in the window:

\[ X_t = (a_1 X_{t-1} + a_2 X_{t-2} + \cdots + a_k X_{t-k}) \bmod m \qquad U_t = X_t / m \]

An LCG is just the case k = 1, with an increment bolted back on. Every time this generator produces a value, the window shifts: the oldest of the k remembered values is dropped, and the new one takes its place at the front.

What this buys you for Monte Carlo

For Monte Carlo work, the statistics that matter most are simple ones: does the output stream have mean ≈ 0.5 and variance ≈ 1/12, the values a true U(0,1) sequence would have — and, just as important, are consecutive outputs uncorrelated with each other? A generator can pass the first test and still fail the second, which is exactly the kind of structure a bad choice of a, c, or m produces.
